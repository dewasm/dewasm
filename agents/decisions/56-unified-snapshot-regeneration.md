# Decision 56: One Command Regenerates Every Execution Snapshot

Status: **Accepted, 2026-08-01.**
Implemented: a `update-snapshots [filter]` xtask subcommand replaces the former `update-repl-snapshot` / `update-doom-snapshot` pair, driven by capture entry points in `crates/dewasm-test-helper` (`capture_app_stdout`, `capture_gzip_compress`, `capture_fs_app_stdout`, the existing `capture_qjs_repl_transcript`) plus the embedded-wasmtime DOOM frame folded in from `crates/xtask/src/doom_snapshot.rs` (which also emits a `doom_frame.png` rendering of the same frame for human inspection, not compared by any test).
All ten checked-in execution snapshots regenerate byte-identically from the clean tree.

## Context

The repo checks in ten execution snapshots, files that record "what running the pinned binary produces": the app-stdout files, the gzip stream, the filesystem-app stdout, the interactive-REPL transcript, and the DOOM frame (all under `examples/apps/snapshots/`, the DOOM frame as `doom_frame.ppm`).
Each has a compare-only test that fails when the file drifts; none of those tests self-update (that is deliberate: an env-var "update mode" on a compare test lets a wrong capture overwrite the thing it was meant to catch, so the tests stay compare-only, decision 27).

Regeneration, though, was uneven.
Two snapshots had xtask commands (`update-repl-snapshot`, `update-doom-snapshot`); the other eight were regenerated by hand-typed `wasmtime run … > examples/apps/snapshots/<case>.stdout` redirection: the exact argv, stdin fixture, `--dir`/`--env` mounts, and output path retyped per case from docs/testing.md prose.
That is error-prone (a wrong redirect writes a plausible-looking but wrong file) and undocumented per case (the filesystem cases' preopens and the two-run sqlite sequence were never spelled out as commands).
Meanwhile the machinery to reproduce every one of these exactly already existed: the `Wasmtime` `BackendUnderTest` (`crates/dewasm-test-helper/src/wasmtime_backend.rs`) is what the freshness suite drives through the shared `apps`/`gzip`/`fs_apps` runners.
The capture side was simply never wired to it.

## Decision

Add one subcommand, **`cargo xtask update-snapshots [filter]`**, that regenerates every execution snapshot, and delete the two bespoke commands.

- **Capture reuses the compare-time runners.**
  New `pub fn` capture entry points in the test-helper crate sit next to the compare-only runners and drive the same `Wasmtime` backend: `capture_app_stdout` / `capture_gzip_compress` (`apps.rs`) and `capture_fs_app_stdout` (`apps_fs.rs`, sharing a new `drive_fs_app_case` core with `run_fs_app_case` so staging, preopens, and the multi-run sequence are defined once).
  The compare-only tests stay compare-only: capture is a separate code path, not a flag on them.

- **One case → snapshot-file mapping, encoded once.**
  `dewasm_test_helper::wasmtime_snapshots()` is the registry: each of the nine wasmtime-CLI snapshots as a `{ label, path, capture }` triple.
  The mapping is the `<case>.stdout` / `.gz` / `.transcript` convention under `apps_snapshot_dir()`.
  The filesystem cases pin *which* run produces the file (the one run whose `expect_stdout` is `Some`; the sqlite create run, `expect_stdout: None`, still executes to leave the DB file, but its stdout is not the snapshot), so the captured bytes byte-match the `include_str!` the case compares against.

- **The DOOM frame stays on the embedded wasmtime crate.**
  `doom.wasm`'s custom-import interface can't run under `wasmtime run` (decision 53), so its capture keeps driving the embedded `wasmtime` crate, an xtask-only dependency that must never enter the test-helper crate's tree.
  xtask folds that one target into the same loop as the nine registry targets; the helper crate stays wasmtime-crate-free.
  That target writes two files: the compared `doom_frame.ppm` oracle plus a `doom_frame.png` rendering of the same frame for human inspection (the DOOM README), never compared by a test.

- **Optional substring filter, fail-loud.**
  No filter regenerates all ten; a filter limits to snapshots whose repo-relative label contains it (`update-snapshots doom`, `update-snapshots cowsay`).
  One line per file written.
  A filter matching nothing is an error, not a silent no-op.
  Missing cache / missing `wasmtime` fails loud with the existing setup message (decision 15).

**Discriminating criterion:** *a snapshot's regeneration should reuse the exact runner its compare test already trusts, invoked from one command, never a hand-retyped shell pipeline whose correctness is unchecked.
Capture and compare share the runner but not a code path, so reuse never becomes a self-approving update mode on the test.*

## Rejected alternatives

- **A per-snapshot command each (the status quo, extended).**
  Keep `update-repl-snapshot` / `update-doom-snapshot` and add seven more.
  It scales the surface with the snapshot count, re-derives the invocation per command, and leaves no single "regenerate everything" entry, the very fragmentation that left eight snapshots on manual redirection.
  One command with a filter gives the same targeting without N commands.

- **An env-var update mode on the compare-only tests** (`DEWASM_UPDATE_SNAPSHOTS=1 cargo test …`).
  Tempting because the test already computes the fresh bytes.
  Rejected on standing policy (decision 27, docs/testing.md): a compare test that can rewrite its own reference can launder a broken capture into a passing run, defeating the check.
  Capture stays a separate path that never runs inside the assertion.

- **Leave the manual `wasmtime run >` redirection documented but uncodified.**
  The prose can't encode the filesystem cases' preopens or the two-run sqlite sequence without becoming a second, drift-prone copy of the runner logic.
  Codifying the mapping once in `wasmtime_snapshots()` removes the retyping and the drift.

## Consequences

- Positive: `cargo xtask update-snapshots` on a clean tree reproduces all ten files byte-for-byte, so a non-empty `git status` afterward is a real signal (a capture bug or genuine nondeterminism), not routine churn.
  Re-pinning an app is now: fetch, `update-snapshots <name>`, re-run the `wasmtime_test` freshness suite, adjust `expect_code` if the exit status moved.
- Positive: the case → file mapping lives in one registry, not scattered across docs prose and shell history; a new snapshot is one registry row.
- Negative / carry-over: the registry is hand-maintained: a new execution snapshot needs its row (and, if it can't go through `wasmtime run`, the same embedded-crate treatment DOOM gets in xtask).
  The DOOM path remains the one target not driven by the shared CLI backend; that asymmetry is inherent to its custom-import interface (decision 53), not incidental.
