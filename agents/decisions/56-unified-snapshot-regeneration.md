# Decision 56: One Command Regenerates Every Execution Snapshot

Status: **Accepted, 2026-08-01.**
Implemented: an `update-snapshots [filter]` xtask subcommand replaces the former pair of commands.
That pair was `update-repl-snapshot` / `update-doom-snapshot`.
The subcommand is driven by capture entry points in `crates/dewasm-test-helper`.
The new ones are `capture_app_stdout`, `capture_gzip_compress`, and `capture_fs_app_stdout`.
The existing `capture_qjs_repl_transcript` is the fourth.
The embedded-wasmtime DOOM frame capture is folded in from `crates/xtask/src/doom_snapshot.rs`.
That capture also emits a `doom_frame.png` rendering of the same frame for human inspection.
No test compares the PNG.
All ten checked-in execution snapshots regenerate byte-identically from the clean tree.

## Context

An execution snapshot is a file that records "what running the pinned binary produces".
The repo checks in ten of them, all under `examples/apps/snapshots/`:

- the app-stdout files;
- the gzip stream;
- the filesystem-app stdout;
- the interactive-REPL transcript;
- the DOOM frame, as `doom_frame.ppm`.

Each has a compare-only test that fails when the file drifts; none of those tests self-update.
That is deliberate.
Suppose a compare test had an env-var "update mode".
Then a wrong capture could overwrite the thing the test was meant to catch.
So the tests stay compare-only (decision 27).

Regeneration, though, was uneven.
Two snapshots had xtask commands (`update-repl-snapshot`, `update-doom-snapshot`).
The other eight were regenerated by a hand-typed redirection.
It had the shape `wasmtime run … > examples/apps/snapshots/<case>.stdout`.
Each case retyped the exact argv, stdin fixture, `--dir`/`--env` mounts, and output path.
The source of each was docs/testing.md prose.
That is error-prone: a wrong redirect writes a plausible-looking but wrong file.
It is also undocumented per case.
The filesystem cases' preopens and the two-run sqlite sequence were never spelled out as commands.
Meanwhile the machinery to reproduce every one of these exactly already existed.
It is the `Wasmtime` `BackendUnderTest` (`crates/dewasm-test-helper/src/wasmtime_backend.rs`).
The freshness suite drives it through the shared `apps`/`gzip`/`fs_apps` runners.
The capture side was simply never connected to it.

## Decision

Add one subcommand that regenerates every execution snapshot: **`cargo xtask update-snapshots [filter]`**.
Delete the two bespoke commands.

- **Capture reuses the compare-time runners.**
  New `pub fn` capture entry points in the test-helper crate sit next to the compare-only runners.
  They drive the same `Wasmtime` backend.
  `capture_app_stdout` / `capture_gzip_compress` live in `apps.rs`.
  `capture_fs_app_stdout` lives in `apps_fs.rs`.
  It shares a new `drive_fs_app_case` core with `run_fs_app_case`.
  So staging, preopens, and the multi-run sequence are defined once.
  The compare-only tests stay compare-only: capture is a separate code path, not a flag on them.

- **One case → snapshot-file mapping, encoded once.**
  `dewasm_test_helper::wasmtime_snapshots()` is the registry.
  It holds each of the nine wasmtime-CLI snapshots as a `{ label, path, capture }` triple.
  The mapping is the `<case>.stdout` / `.gz` / `.transcript` convention under `apps_snapshot_dir()`.
  The filesystem cases pin *which* run produces the file: the one run whose `expect_stdout` is `Some`.
  The sqlite create run (`expect_stdout: None`) still executes to leave the DB file.
  But its stdout is not the snapshot.
  So the captured bytes byte-match the `include_str!` the case compares against.

- **The DOOM frame stays on the embedded wasmtime crate.**
  `doom.wasm`'s custom-import interface can't run under `wasmtime run` (decision 53).
  So its capture keeps driving the embedded `wasmtime` crate.
  That crate is an xtask-only dependency that must never enter the test-helper crate's tree.
  xtask folds that one target into the same loop as the nine registry targets.
  The helper crate stays wasmtime-crate-free.
  That target writes two files.
  One is the compared `doom_frame.ppm` oracle.
  The other is a `doom_frame.png` rendering of the same frame for human inspection (the DOOM README).
  No test ever compares the PNG.

- **Optional substring filter, fail-loud.**
  No filter regenerates all ten.
  A filter limits to snapshots whose repo-relative label contains it.
  Examples are `update-snapshots doom` and `update-snapshots cowsay`.
  One line per file written.
  A filter matching nothing is an error, not a silent no-op.
  Missing cache / missing `wasmtime` fails loud with the existing setup message (decision 15).

**Discriminating criterion:** *regenerate a snapshot with the same runner its compare test trusts.*
*Invoke it from one command, never a hand-retyped shell pipeline whose correctness is unchecked.*
*Capture and compare share the runner but not a code path.*
*So reuse never becomes a self-approving update mode on the test.*

## Rejected alternatives

- **A per-snapshot command each (the status quo, extended).**
  Keep `update-repl-snapshot` / `update-doom-snapshot` and add seven more.
  It scales the surface with the snapshot count and re-derives the invocation per command.
  It also leaves no single "regenerate everything" entry.
  That fragmentation is what left eight snapshots on manual redirection.
  One command with a filter gives the same targeting without N commands.

- **An env-var update mode on the compare-only tests** (`DEWASM_UPDATE_SNAPSHOTS=1 cargo test …`).
  Tempting because the test already computes the fresh bytes.
  Rejected on standing policy (decision 27, docs/testing.md).
  A compare test that can rewrite its own reference can launder a broken capture into a passing run.
  That defeats the check.
  Capture stays a separate path that never runs inside the assertion.

- **Leave the manual `wasmtime run >` redirection documented but uncodified.**
  The prose can't encode the filesystem cases' preopens or the two-run sqlite sequence.
  Encoding them would make it a second, drift-prone copy of the runner logic.
  Codifying the mapping once in `wasmtime_snapshots()` removes the retyping and the drift.

## Consequences

- Positive: `cargo xtask update-snapshots` on a clean tree reproduces all ten files byte-for-byte.
  So a non-empty `git status` afterward is a real signal, not routine churn.
  It means a capture bug or genuine nondeterminism.
  Re-pinning an app is now:
  1. fetch;
  2. `update-snapshots <name>`;
  3. re-run the `wasmtime_test` freshness suite;
  4. adjust `expect_code` if the exit status moved.
- Positive: the case → file mapping lives in one registry.
  It is not scattered across docs prose and shell history.
  A new snapshot is one registry row.
- Negative / carry-over: the registry is hand-maintained: a new execution snapshot needs its row.
  A snapshot may be unable to go through `wasmtime run`.
  It then also needs the same embedded-crate treatment DOOM gets in xtask.
  The DOOM path remains the one target not driven by the shared CLI backend.
  That asymmetry is inherent to its custom-import interface (decision 53), not incidental.
